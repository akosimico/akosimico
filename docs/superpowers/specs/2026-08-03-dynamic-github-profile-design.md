# Dynamic GitHub Profile Card Design

## Objective

Replace the profile repository's static banner with a GitHub-native light/dark SVG identity card regenerated by GitHub Actions from the complete repository inventory visible to one or more authenticated credentials. Preserve the Lucifer Rodstark, Ph.D. persona and the existing enterprise/agentic theme without exposing legal identity, personal contact information, employer/client names, educational institutions, repository names, organization names inside generated telemetry, or the source portrait.

## Reference Behavior

The implementation retains the useful parts of Andrew6rant/Andrew6rant:

- a minimal README embeds separate dark-mode and light-mode SVGs through `<picture>`;
- a scheduled GitHub Actions workflow collects account statistics;
- generated SVG files are committed back to the profile repository;
- stable SVG element IDs provide machine-readable fields.

It deliberately does not copy the original recursive all-history line-count scanner. That method is not viable for accounts containing extremely large or synthetic histories, and cumulative additions minus deletions is not current source LOC.

## Account Coverage

For every supplied token, the collector calls `GET /user/repos` separately for all three authenticated affiliations:

- `owner`;
- `collaborator`;
- `organization_member`.

Each request uses `visibility=all` and complete pagination. Results from every token and affiliation are merged and deduplicated by immutable numeric repository ID. A repository may be visible through multiple credentials or carry multiple affiliation labels, but appears exactly once in the total. Primary classification precedence is `owner`, then `organization_member`, then `collaborator`.

The public outputs contain aggregate counts only:

- total repositories;
- owner, organization-member, and collaborator classification;
- public, private, and internal visibility counts;
- archived, fork, and disabled counts;
- unique accessible organization-owner and resource-owner counts;
- GitHub-reported aggregate repository size;
- stars on personally owned repositories;
- account followers;
- all-time GitHub commit-contribution count collected in one-year GraphQL windows;
- generation timestamp and coverage state.

No repository names, IDs, URLs, descriptions, branch names, commit messages, organization names, language fingerprints, or per-repository statistics are written to the public repository.

## Completeness and Validation

A successful run means:

1. at least one token is supplied;
2. every token authenticates as `itsmfknlucy`;
3. all token sources return consistent account creation metadata;
4. all three affiliation inventories complete for every token without an API or pagination error;
5. every returned repository is normalized and deduplicated;
6. every resource owner configured in `PROFILE_REQUIRED_OWNERS` is represented in the merged inventory;
7. all yearly contribution queries complete through the primary token;
8. both generated SVG documents parse as valid XML;
9. aggregate invariants hold, including visibility totals and primary-affiliation totals equaling the unique repository total.

If any condition fails, generation exits before replacing existing assets. The last verified SVG files remain published.

## Authentication

Credentials are supplied exclusively through encrypted GitHub Actions secrets and environment variables:

- `PROFILE_STATS_TOKEN` accepts one broad read-only token; and
- `PROFILE_STATS_TOKENS` accepts a newline-separated collection of read-only tokens.

The workflow builds `PROFILE_STATS_TOKENS` from the primary personal-account secret and optional per-organization secrets. This is required because a fine-grained personal access token is restricted to one selected resource owner. One fine-grained token therefore cannot cover a personal account and several organization owners. The supported configurations are:

1. one broad token that can read the personal account and every required organization; or
2. one fine-grained token per resource owner, all authenticating as the same GitHub user.

The first token is the primary identity token. It supplies account-level follower and contribution signals. All supplied tokens participate in repository inventory. Tokens are deduplicated in memory, excluded from object representations, never accepted as command-line arguments, never serialized, never cached, never printed, and never embedded in generated output. The workflow uses the repository-scoped `GITHUB_TOKEN` only to commit generated assets.

Every token must be authorized for all intended repositories under its selected resource owner. Organization approval or SSO authorization may also be required. A token pasted into chat, an issue, a commit, a log, a screenshot, or a workflow file is considered compromised and must be revoked.

## Architecture

### `profile_generator/api.py`

A dependency-free GitHub REST/GraphQL client using `urllib.request`, explicit timeouts, bounded retries for transient responses, GraphQL error detection, JSON shape validation, and full page traversal.

### `profile_generator/models.py`

Immutable dataclasses for repository inventory and rendered profile statistics, invariant validation, and stable aggregate-only JSON serialization.

### `profile_generator/collector.py`

Multi-token authentication validation, three-affiliation discovery per token, repository-ID deduplication, affiliation precedence, aggregate classification, required-owner validation, invariant checks, and yearly contribution collection through the primary token.

### `profile_generator/render.py`

GitHub-compatible SVG generation using standard XML-safe text and `<tspan>` elements only. No JavaScript, external fonts, `foreignObject`, remote assets, or embedded source image.

### `profile_generator/cli.py`

Environment-only configuration, token-list normalization, fail-before-write orchestration, atomic output replacement, public aggregate JSON generation, and concise aggregate-only logging.

### GitHub Actions

A scheduled and manually dispatchable workflow using current Node 24-compatible official actions, Python 3.13, standard-library unit and contract tests, XML/JSON validation, tracked-file credential scanning, and bot commits only when generated files change. Until a primary encrypted secret exists, the workflow completes tests and compilation, preserves the bootstrap assets, and skips authenticated generation.

## Error Handling

- Missing token: fail with the secret names, never a value.
- Wrong authenticated login on any token: fail before publishing.
- Inconsistent account metadata across tokens: fail before publishing.
- Missing required resource owner: fail before rendering.
- API 401/403: fail without dumping response bodies that may contain private metadata.
- Rate-limit exhaustion: retry only within a bounded wait; otherwise fail and preserve previous assets.
- 5xx responses: bounded exponential retry.
- GraphQL `errors`: fail even when HTTP status is 200.
- Malformed repository payload: fail instead of skipping silently.
- Invalid generated XML, JSON contract, or aggregate invariant: fail before replacement.

## Testing

The standard-library `unittest` suite covers:

- REST pagination;
- transient retry and GraphQL-error handling;
- multi-token inventory merging;
- repository-ID deduplication across credentials and affiliation lists;
- primary-affiliation classification;
- public/private/internal and state counts;
- required-owner rejection;
- contribution-window boundaries;
- aggregate invariants;
- XML escaping and SVG parseability;
- aggregate-only JSON output;
- atomic replacement behavior;
- README/workflow repository contracts;
- source-identity and token-leak privacy contracts.

## Non-Goals

- Exposing repository names or private metadata.
- Traversing every commit in every repository.
- Publishing cumulative additions/deletions as "lines of code."
- Cloning repositories.
- Embedding the original portrait or CV.
- Publishing legal-name, contact, employment, client, institution, or credential identifiers.
